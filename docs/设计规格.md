# MySQL 深水区八股（主从 / 在线 DDL / 分库分表 / PITR）· Track 设计规格

> 状态：设计稿（未开工）· 对应平台契约见 [`_CONTRACT.md`](./_CONTRACT.md)
> 一句话定位：给「数据库八股已经背过一轮、但主从/DDL/分片/恢复只敢说不敢碰」的 Java 后端，
> 一条**离线可在自己笔记本上复现**的深水区练习线——每个考点都有一台真 MySQL 8.0 让它变红、变绿。

**卖点（三条以内）**：

1. **把「只能文字了解」的考点变成了红绿判据**。主从延迟、binlog 三格式、INSTANT DDL、跨库分页、
   时间点恢复——每一个都有「骨架上就是错的」那条用例，而不是一段背下来的话。
2. **抖动指标一律不许当唯一判据**。延迟用 `SOURCE_DELAY` 造出确定的方向、用「行数据在不在」的
   屏障收敛做硬断言；「慢」用固定数据集上的扫描行数（digest 表 + Handler 计数器）而不是毫秒。
   §1.4 把每个考点的「怎么让它确定」逐条写出来了，§1.5 把只能可观测的诚实列出。
3. **判据测行为，不测手法**。路由可以自己手写、也可以用骨架已备好的 ShardingSphere-JDBC 坐标；
   DDL 可以 INSTANT、也可以走影子表搬迁——只要可观测契约对得上就绿。

> ① 六个 stage 是一条**因果链**（复制语义 → DDL 与锁 → 分片 → 恢复 → 证据闭环 → 一致性取舍），
> 相邻两个 stage 的考点没有一个是另一个的子集；合任何一对都会把「A 的判据」与「B 的判据」挤进同一张
> ticket，红就不再「只红在本 stage 的考点上」，而 §1.2 的整段论证就靠这条。
> ② 合并必须重算 `progression.prerequisites` 与整条分支链。本 Track 的链已经在 §3 论证过「每一关
> 只 merge 一个 ref、只加不删」（`_CONTRACT.md` §5 是链式 `git merge`，不是 DAG）；合并会把
> 「上一阶段是单数」这个前提打掉，`-sol` 的切出点也就没有唯一定义。**本轮零合并的直接收益就是
> §3 那张表、分支名、切出点与 `git log --oneline` 的自检全部零改动。**
> ③ 六个 stage 都**扩得到**，而且扩面素材正是 `_SCALE.md` §2 点名的那三类：
> 「统计/口径」（复制进度台账、恢复轮次台账、统计快照口径、路由决策审计口径）、
> 「编排与工具」（影子表迁移的重放日志、两段式发号的号段租约、PITR 的多步可重跑路径）、
> 「边界与拒绝」（binlog 位点已被保留期甩掉、拿不到 DDL 锁、被中断的迁移重跑、备份/位点不可用、
> 空结果集、从库不可读）。这三类与核心方法**共享同一套语义**，所以扩面不引入考点族之外的噪音。
>
> **扩面时守住了 `_SCALE.md` §1.1 的三条约束**：
> ① 新增缺陷全部是「**单线程/单机顺序执行时是对的，并发或故障才错**」的形态——丢更新、检查-然后-行动、
> 复合不变量、有界重放的重复执行、资源上限被击穿。四个新增文件（`V1__…replication_progress.sql`、
> `TwoSegmentIdAllocator`、`PitrRunLedger` + `V4__…`、`StatsSnapshotProvider`、`RouteDecisionProvider`
> + `V6__…`）在单线程下**全部走完正常路径**：进度台账能算出一致的 gap、号段补充器串行补货正确、
> 恢复台账能记完一轮、统计快照能抓齐三项读数、决策审计能读回本次决策。因此环境体检
> `SmokeTest`（`@Tag("stage00")`）在这 7 处新增的存在下**仍然全绿**——这是本 Track 的第一原则
> （骨架功能是通的，缺的只是复制/锁/恢复/一致性语义）。
> ② 本 Track **一处都没有用「单线程可见」的形态**，所以 `_SCALE.md` §1.1 第 3 条那三项额外要求
> （确定性序列复现 + 点名类别）本轮不适用。唯一近似的是 stage 2 的 `interruptedMigration_isResumable`：
> 它是**确定性序列复现的业务缺陷**（先让迁移器在第 k 批之后抛错、再原样重跑一次，直接按顺序调 API
> 把那个序列做出来，不靠竞态碰运气），但它**单线程下仍然是错的**（第二次会在库上留下第二个影子表），
> 因此它按 §1.1 约束 3 在 §2.3 与 Ticket 2 的题面里**点名了类别**，并单独论证它不破坏

> ③ 新增判据没有一条是抖动的：新增的量全是**离散计数与状态迁移**（台账行数与 gap 之和、批次数、
> 已发布覆盖区间、快照的三项读数、决策记录条数），逐条论证见扩写后的 §1.4 与 §1.5。

### 1.1 逐 stage 红在哪

「红」的定义与平台一致：**该 stage 的 canonical 测试组在骨架上至少有一条用例失败**，且失败原因必须是
业务缺陷。每张下面都同时列出「骨架上本来就绿的用例」——它们的存在本身就是证据，说明这组测试
不是「永远红」的废测试（与 `seckill-lab` stage-02 三绿一红的形状同构）。

| stage | canonical 用例（红加粗；**基线**=单线程/正常链路对照用例；*边界*=边界或拒绝路径） | 骨架为什么红（红分属哪个不变量） |
|---|---|---|
| 1 主从与延迟 | **`sqlThreadStopped_isNotUsableForReads`**（红·不变量「SQL 线程停掉的从库不得被判成可读」）、**`unknownLag_mustNotBeTreatedAsUpToDate`**（红·不变量「延迟未知 ≠ 无延迟」）、**`rowFormat_auditMustSeeRowEvents`**（红·不变量「ROW 格式下这次变更必须可见」）、`healthyReplica_isUsableForReads`（基线）、`lagSample_upToDateOnlyWhenProbeRowVisible`（基线）、`replicaProgress_advancesMonotonicallyOnReplay`（基线·统计口径）、`progressLedger_gapEqualsPositionDifference`（基线·统计口径）、*`progressLedger_rejectsLostPositionRange`*（边界：位点已被 binlog 保留期甩掉） | 三条红分属**三个不同不变量**：①`ReplicationHealthService.isUsableForReads()` 只看 `ioRunning`（缺的是「IO 与 SQL 是两个可以分别停住的阶段」）②同类的 `LagSample.upToDate()` 把 `secondsBehindMaster == null` 当成「不落后」（缺的是「未知是一个独立的第三态」）③`BinlogInspector.eventsOf(file)` 只保留 `Query` 事件，ROW 格式下返回空表（缺的是「ROW 把语句文本换成行镜像」）。把 ① 修好不会让 ② 或 ③ 变绿，反之亦然——这不是同一个 bug 的三种写法 |

### 1.2 红为什么「红在对的地方」

**先把三种「错误的红」排除掉**，它们是准入门的假阳性来源：

- **不是编译错**：六个 stage 的改动面在骨架上**类与签名都已经存在且能编译**（`ReplicationHealthService`、
  `ReplicationStatusSource`、`BinlogInspector`、`OnlineDdlGuard`、`ShadowTableMigrator`、`ShardRouter`、
  `ShardOrderRepository`、`GlobalIdGenerator`、`TwoSegmentIdAllocator`、`PitrRestoreTool`、`PitrRunLedger`、
  `ContainerCliRunner`、`SlowQueryTriageService`、`StatsSnapshotProvider`、`ReadWriteRoutingService`、
  `RouteDecisionProvider` 全部有可编译的骨架实现），所以 `mvn -DskipTests compile` 在六个阶段分支上都成功
  ——这是准入门的第一条硬门，也是本 Track 与「让学员从零写一个类」的分界线。**v1.1 新增的 7 处**
  （两个 Java 口径类、一个发号编排类、一个恢复台账类、四个 SQL 迁移脚本中的新增三处、一个 CLI 边界类）
  同样都是「签名齐、单线程路径走得通、只是语义不对」的骨架，不是空文件。
- **不是装配失败**：四个 MySQL 实例由 compose 起、`dbdeep-master` 的 `healthcheck` 用
  `mysqladmin ping -h 127.0.0.1`（**必须走 TCP**，`seckill-lab` 已经踩过 unix socket 假 healthy 的坑），
  冒烟测试 `SmokeTest`（`@Tag("stage00")`）在骨架上全绿：四个实例可连、复制 IO/SQL 双 Yes、
  `binlog_format=ROW`、容器内 `mysqldump`/`mysqlbinlog` 存在。【v1.1 复核】新增的四个迁移脚本
  （`V1__stage01_replication_progress.sql` / `V4__stage04_pitr_run_ledger.sql` /
  `V6__stage06_route_decision.sql` / `V5__stage05_slow_sql_index.sql`）与两个口径类在冒烟阶段
  **都能建表、能读回、能跑完一轮正常路径**，冒烟测试因此在扩面后仍然全绿——这是本 Track 的第一原则
  （`_SCALE.md` §1.1 约束 1）。跑不通就是环境问题，不是学员的问题。
- **不是「测试写空」**：每个 stage 的 canonical 测试都**自带 fixture 与期望值**（见 §2 的
  「每 stage 独立表」约定），不依赖被测代码产出的中间物。**v1.1 复核**：新增的 20 条用例全部沿用这条约定
  ——进度台账的 fixture 由测试自己按固定序列写 `repl_progress_snapshot`，恢复轮次账由测试自己造一行，
  统计快照与路由审计同理；没有一条断言依赖「被测代码先写对一步」。

**再看每一处红为什么是业务缺陷**（一句话版本，逐张 ticket 的 `expect` 里有完整版）：

1. stage 1 的红是**运维判断错了**：把一个 SQL 线程已经停掉的从库判成「可读」。这不是「功能没实现」，
   而是「实现了但结果与事实相反」，是最难在 code review 里看出来的那类缺陷。另外两条红同样是判断错：
   「算不出延迟」被当成「没有延迟」、「ROW 格式下语句文本消失」被当成「什么都没发生」。
2. stage 2 的红是**运维动作把业务写死了**：排队中的 DDL 会让它之后到达的写请求一起超时。
   这条红由我们自己**持有一个未提交事务**制造出确定的前置条件，不靠压测、不靠碰运气。
   v1.1 新增的第四条红是**「重跑一次就好了」这个直觉错了**：被中断的影子表迁移在第二次执行时
   会在库上留下第二个影子表，并且已回填的区间被重搬一遍——它是**确定性序列复现的逻辑缺陷**，
   不是竞态（见 §2.3 的 D-P 与 Ticket 2 的 `expect`）。
3. stage 3 的红是**数据读错了**：第二页有重复行和丢行、写完读不到。都是纯数据断言。
   v1.1 把「两段式发号的号段补货」纳入后，第三条红多了一层「并发补货时同一份号段被两个实例同时领走」——
   它由**唯一键**这一确定性事实兜住，仍然不依赖计时。
4. stage 4 的红是**恢复结果与目标状态不一致**：少 10 行（全备没灌）或多出 3 行（越过了停止位点）。
   v1.1 新增的第四条红是**输入不可用时「看起来跑完了」**：备份文件不存在或停止位点早于可重放区间时，
   工具应该**拒绝**，而不是灌进去一半数据——这是恢复演练里最难发现的一类事故。
5. stage 5 的红是**挑错了治理对象**，以及**给出的证据恒为空**——治理闭环断在「证明」这一步。
6. stage 6 的红是**一致性契约没兑现**：写后读读到旧值，且系统还声称自己是最新的。
   v1.1 新增的第四条红是**审计口径自己不可信**：决策记录被保留策略淘汰之后，读数不能把「被淘汰」
   当成「零决策」——否则「路由可归因」这句话在最需要它的时刻失效。

### 1.4 确定性论证（「怎么让它确定」逐条）

这是本 Track 与「拿毫秒数当判据」的分水岭。四条通用手法：**造确定的前置条件**、**用屏障等待替代
延迟阈值**、**用计数/集合替代耗时**、**用桩把服务器造不出来的状态造出来**。

| 考点 | 漂在哪 | 本 Track 怎么让它确定 |
|---|---|---|
| 复制延迟 | 真实延迟随负载抖动，`Seconds_Behind_Master` 会跳、会为 NULL | ①要「确定落后」就用 `CHANGE REPLICATION SOURCE TO SOURCE_DELAY=30`（**故意**让从库慢半拍，方向确定）；②要「确定不追」就 `STOP REPLICA SQL_THREAD`（从库被冻住，落后是必然，不是概率）；③收敛判断一律用**探针行屏障**：主库插 `repl_probe(seq)`，轮询从库直到该 seq 出现，超时 90s。断言的是「最终收敛」，不是「多少毫秒内收敛」 |
| `Seconds_Behind_Master` 为 NULL | 服务器端造不出稳定复现 | **用桩造**：`ReplicationStatusSource` 是骨架的注入点，canonical 测试注入一个 `secondsBehindMaster=null` 的桩状态，断言「未知 ≠ 无延迟」。这条用例完全不碰数据库，因此 100% 确定 |
| binlog 事件形态 | 事件条数受 `binlog_row_event_max_size` 分批策略影响，版本间会变 | **断事件类型与 Info 文本，不断条数**：`SHOW BINLOG EVENTS IN '<file>'` 里 ROW 格式出现 `Update_rows` 且没有含语句文本的 `Query` 事件；STATEMENT 格式反之。每次只改**会话级** `binlog_format`（`SET SESSION`），GLOBAL 值全程钉死 `ROW`，避免污染复制与后续用例 |
| DDL 是否重建了表 | 「ALTER 期间业务没被阻塞」在小表上根本观察不到（ALTER 毫秒级完成） | **换证据源**：`information_schema.INNODB_TABLES` 的 `TOTAL_ROW_VERSIONS` / `INSTANT_COLS` 是**事后**可读的元数据事实，二值、与机器快慢无关。每次 ALTER 前由 fixture 重建 `orders_ddl` 表，所以「本表自建表以来发生过 instant 变更」是非黑即白的 |
| DDL 阻塞窗口 | 想观测「阻塞了几秒」必然抖 | **不用等，主动持锁造出确定的前置条件**：fixture 会话 S1 开事务并对表做一次快照读（持 MDL-S），S2 线程发起 ALTER（排 MDL-X 队列），随后 W 会话的 `INSERT` 设 `lock_wait_timeout=2`。此时 W 必然被队列挡住 → 断言「W 报 1205 超时」与「`performance_schema.metadata_locks` 里有 `PENDING` 的 X 锁」。这是排队语义，不是计时 |
| 跨库分页 | 「性能」不可判 | **只判正确性**：固定 20 行、固定排序键，断言第 2 页的**集合恒等**（无重、无漏）。排序键末位带 `id` 兜底，消除同值行的顺序歧义 |
| 全局 ID | 依赖真实时钟会抖 | `GlobalIdGenerator` 从骨架起就接受 `LongSupplier clockMillis`（依赖注入），测试注入**固定时钟**：两个实例同一时刻取号，断言并集无重复。时钟回拨同理——注入一个先前进后退的时钟序列，断言单调不减 |
| PITR 的恢复边界 | `--stop-datetime` 依赖 binlog 事件时间戳，同秒多事务会切在事务中间 | **硬判据一律用 position**：停止位点由测试在「误删之前」直接读 `SHOW MASTER STATUS` 得到（这是一次真实的位点读取，不是猜的）。`--stop-datetime` 只作为 `docs/pitr演练手册.md` 里的可观测说明 |
| 「慢」查询 | `long_query_time` 是时间的，机器一快就不报，阈值一调就漏 | **换判据**：`performance_schema.events_statements_summary_by_digest.ROWS_EXAMINED`（固定数据集上的扫描行数）+ 会话 `Handler_read_rnd_next` 增量。同一份 5 万行数据重跑得到同一量级，与 CPU 快慢无关 |
| 半同步复制 | 插件可用性、ACK 延迟都与环境相关 | **降级为可观测**：插件装得上就记录 `Rpl_semi_sync_source_status`，装不上也**不判 fail**（见 §1.5） |
| **【v1.1】被中断的迁移重跑** | 「中断」本身在真机上没有稳定触发点（要看什么时候被人 KILL） | **用确定性序列复现**：迁移器的批处理循环暴露一个 `stopAfterBatch` 构造参数（骨架里就有），测试传 `k=2` 让它**在第 2 批之后抛错**，再把参数改回「跑完」原样重跑一次。整个序列由测试按顺序调用两次 API 做出来，不靠任何竞态、不看时间；断言的是**集合与计数**：库里影子表数量 == 1、两次执行覆盖的批次区间恰好铺满且不重叠、切换后终态与一次跑通逐行相同 |
| **【v1.1】两段式发号的号段补货** | 「两个实例同时补货」如果靠线程竞争去碰，可能不撞 | **把唯一性交给数据库的约束，而不是交给时序**：`id_lease` 上对 `(worker_id, segment_lo)` 有唯一键，测试用一个固定闸门让两个分配器**同一时刻**发起补货，断言的是「`id_lease` 里同一号段恰好一行」+「两次取号的并集不重叠」这两个**离散事实**；即使这次恰好没撞，唯一起作用的前提也是那条唯一键，因此重复跑结论一致 |
| **【v1.1】恢复轮次台账的读数** | 「跑了几轮」若按时间窗口统计就会抖 | **按轮次主键数**：`pitr_run_ledger` 每次 `restore()` 无论成败都恰好写一行，`attemptNo` 从 1 起单调递增；断言「两次恢复 ⇒ 恰好两行且 `status` 分别是 `COMPLETED`/`COMPLETED`」，「被拒绝的一次 ⇒ 恰好一行且 `status=REJECTED`」。这是纯计数，与时间、机器都无关 |
| **【v1.1】统计快照的三项读数** | 访问路径 / `Handler` 计数器 / 语义校验和若分三次查询，中间会被别的语句污染 | **一次抓齐、且用会话内不复位的差分**：`StatsSnapshotProvider.take()` 在同一个会话里先 `FLUSH STATUS` 再依次跑基线语句与改写语句，把三项读数装进一个不可变快照；断言用「后一项 ≥ 前一项 × 100」的**相对关系**与「校验和逐个相等」，不用任何绝对耗时 |
| **【v1.1】决策审计的保留口径** | 「审计被淘汰了几条」在真实系统里取决于清理计划何时跑 | **把保留策略做成构造参数、淘汰动作做成显式方法**：测试先写入 N 条决策、再调 `evictBeyond(k)`、最后断言 `evictedCount == N - k` 且剩余记录仍是最近的 k 条。淘汰是测试**主动触发**的一次普通方法调用，不是后台线程，因此 100% 确定 |

### 1.5 只能「可观测」、不进 canonical 测试的考点（诚实清单）

写进判据会让这条 Track 变成 flaky 收集器，所以它们只进报告与答辩文本：

1. **延迟的绝对数值与曲线**：`Seconds_Behind_Master` 的具体值、延迟随时间的变化。报告里记，
   不参与红绿。
2. **DDL 的耗时与「期间写入成功率」**：小表上 ALTER 毫秒级完成，「业务没被阻塞」在实验室尺度
   不可判。确定性的替代判据是元数据证据（§1.4）+ MDL 队列语义。
3. **gh-ost / pt-osc 的实机行为**：binlog 增量追赶、限速（throttle）、cut-over 的可见窗口。
   本 Track 只要求影子表方案的**可判部分**（分批回填计数 + 原子改名后的终态），不要求引入外部二进制。
4. **跨库分页的性能差异**（内存归并 vs 二次查询）：只判正确性，性能只写进答辩。
5. **按时间点恢复（`--stop-datetime`）的精确性**：同秒内多事务的边界不可靠，只做可观测。
6. **PITR 的 RTO（恢复耗时）**：记进报告，不判。
7. **半同步复制的延迟/吞吐代价、以及无损复制的语义**：环境相关，只观测插件状态与
   `Rpl_semi_sync_source_no_tx` 等计数器。
8. **复制线程的 CPU、relay log 大小、`innodb` 内部等待事件**：属性能观测，不属判据。
9. **【v1.1 新增】SQL 迁移脚本的执行耗时与「一次跑完要多久」**：`V1`/`V4`/`V5`/`V6` 四个脚本都设计成
   **幂等且可重放**（`CREATE TABLE IF NOT EXISTS` / `DROP … IF EXISTS` + 重建），因此它们的判据是
   「重放两次结果相同」这条离散事实，而不是「第二次快了多少」。脚本耗时只进报告。
10. **【v1.1 新增】台账的口径与真实服务器指标的一致性程度**：`repl_progress_snapshot` 的 `lagSeconds`
    与 `SHOW REPLICA STATUS` 的 `Seconds_Behind_Master` 在采样瞬间的差值、`pitr_run_ledger` 里记录的
    恢复秒数、`route_decision` 的写入延迟——都只记不判。判的是**台账内部自洽**（gap 之和 = 位点之差、
    轮次主键单调、每次读恰好一条），因为这些是离散且可复算的。

### 1.6 不可判定或需要妥协的考点

- **「两阶段提交（redo/binlog 一致性）」不可在实验室稳定观测**：要复现「binlog 写完、redo 未提交
  时 crash」需要精确控制注入崩溃点（`innodb_flush_log_at_trx_commit`、kill -9 时序），
  重复性差且会污染卷。**妥协**：作为 stage 4 八股地图里的文字考点 + `docs/pitr演练手册.md` 的
  「为什么 binlog 能补上 PITR 这一步」一节，不进 canonical 测试。
- **GTID / 组复制 / MGR / XtraBackup / Canal 等**：全部列入地图附录「本 Track 不涉及、该文字了解」。
- **扩容迁移（翻倍扩容搬数据）**：需要多轮数据搬迁+对账，工作量超出单 stage。只在地图里成表。
- **两个 shard 复用同一 mysqld**：见 §7 风险表第 2 条——路由/分页/全局 ID 的教学点不受影响，
  唯一丢失的是「跨实例网络」这一层（而那一层本来也没有判据可验）。

### 2.2 分层与约定

**四个数据源显式注入，不做隐式路由。** `config/` 里提供四个 `JdbcTemplate` bean：
`masterJdbc`、`replicaJdbc`、`shardJdbc(ds0/ds1)`、`restoreJdbc`。业务服务**按名字取用**，
只有 `ReadWriteRoutingService`（stage 6）持有那个会「随决策变化」的 `RoutingDataSource`。
这条约定不是洁癖：如果任何一个观测类服务偷偷走了路由数据源，stage 1 的断言就可能因为
「这次读恰好被送去从库」而飘——**判据的确定性从依赖显式化开始**。

**状态源可注入。** `ReplicationStatusSource` 是一个单方法接口（`ReplicationStatus read()`），
生产实现走 `replicaJdbc` 解析 `SHOW REPLICA STATUS`；canonical 测试注入桩实现来构造
「服务器造不出来的状态」（`Seconds_Behind_Master IS NULL`）。这是 §1.4 那条确定性手法在骨架上的落点，
也是 `docs/架构与约定.md` 第 3 节的主题。

**手写 SQL 全部落在 mapper XML**，Java 里不拼 SQL（沿用 `seckill-lab` 的项目规范）。
`ShardOrderRepository` 是唯一例外——分片路由必须自己拼库名与表名，但**一律经
`ShardRouter.shardOf(key)` 拿库名、绝不用 `${}` 拼用户输入**，这条在 `docs/架构与约定.md` 里写死。

**测试与业务表一一隔离。** 每个 stage 有自己的表（`binlog_probe`/`repl_probe`/`repl_progress_snapshot`、
`orders_ddl`、`order_0`+`order_1`+`id_lease`、`ledger_entry`+`pitr_run_ledger`、
`orders_stats`+`slow_query_baseline`、`member_profile`+`route_decision`）。这是链式分支下最容易
出现的假红来源：stage 5 的 fixture 若去复位 `orders`，stage 2 的用例会在同一次 `mvn test` 里被
打红，而学员根本没做错事。

**【v1.1 新增】改动面的三类角色在骨架里怎么摆。** `_SCALE.md` §1 要求每个 stage 的三个改动面文件
分别落在「核心状态/算法」「并发·事务或数据库语义载体」「调用编排或异常·边界路径」上，所以骨架在
分层上把这三类**物理分开**，好让学员一眼看出「这次要协调的是哪三处」：

| 角色 | 归属（包/目录） | 本 Track 的典型成员 | 为什么它必须是独立文件 |
|---|---|---|---|
| ① 核心状态/算法 | `replication/` `ddl/` `sharding/` `slowlog/` `routing/` 的服务类 | `ReplicationHealthService` · `OnlineDdlGuard` · `ShardRouter` · `SlowQueryTriageService` · `ReadWriteRoutingService` | 这里是「结论算错」的那一处；它不改，别的两处再对也没用 |
| ② 并发·事务/DB 语义载体 | `config/` `domain/` `*.sql`（`src/main/resources/db/migration/`） | `ReplicationStatusSource`（位点两阶段的口径）· `ShadowTableMigrator`（分批 + 原子切换）· `TwoSegmentIdAllocator`（号段租约）· `PitrRunLedger` + `V4__…` · `V6__stage06_route_decision.sql` | 「语义」在数据库侧的落点：约束、表结构、位点区间、可重放区间。只改 ① 会让语义没地方落 |
| ③ 调用编排 / 异常·边界路径 | `exec/` `pitr/` `slowlog/` 的口径类与 `*.sql` 迁移脚本 | `ContainerCliRunner`（不可用输入先拒绝）· `PitrRestoreTool`（全备→增量→边界→清靶机）· `StatsSnapshotProvider` · `V2__…` · `V5__…` | 多步动作的先后、失败回滚、以及「输入不可用/拿不到锁/位点耗尽」这三类边界；`_SCALE.md` §2 把它列为扩面的首选落点 |

四个 SQL 迁移脚本因此**不是脚手架**：`V1`/`V4`/`V6` 是 v1.1 新增的口径载体（台账/轮次账/审计表的
结构与口径逻辑），`V2`/`V5` 本来就带缺陷。整份 `src/main/resources/db/migration/` 都是**学员可读可改**
的改动面（与 `src/test/` 这个判定面相反），理由见 §6。

### 2.3 故意留的缺陷（逐条：文件 + 缺陷 + 对应 stage）

「红」的编号 D-A…D-P 与 §1.1 的用例逐条对应；**每条缺陷都满足 `_SCALE.md` §1.1 约束 1**
（骨架单线程/单机顺序执行时是对的，只有并发、故障或不可用输入才错），因此冒烟测试在任何一处
缺陷存在的情况下都是绿的。

| # | 文件 | 缺陷（骨架现状） | stage | 红用例 / 不变量 |
|---|---|---|---|---|
| D-A | `replication/ReplicationHealthService.java` | `isUsableForReads()` 只看 `ioRunning`（SQL 线程停了照样说「可读」） | 1 | `sqlThreadStopped_isNotUsableForReads` |

### 2.4 基础设施

| 服务 | 端口（宿主→容器） | server-id | 关键配置 | 为什么 |
|---|---|---|---|---|
| `dbdeep-master` | 13307→3306 | 1 | `log_bin`、`binlog_format=ROW`、`slow_query_log=ON`、`performance_schema=ON`、`long_query_time=0.1`、`innodb_print_all_deadlocks=ON` | stage 1/2/5 都要主库侧观测；`performance_schema` 是本 Track 唯一的「确定性证据源」（`metadata_locks` + `events_statements_summary_by_digest`） |
| `dbdeep-replica` | 13308→3306 | 2 | 同 master 的种子；`read_only=ON`；`log_bin=ON` + `log_replica_updates=ON` | 从库也写自己的 binlog ——「从库的额外开销本身也是延迟来源」是可观测的；`read_only` 挡普通用户，`super_read_only` 由 bootstrap 脚本在初始化**之后**动态打开（写进 my.cnf 会把 entrypoint 自己的初始化挡死） |
| `dbdeep-shard` | 13309→3306 | 3 | 内含 `shard_0`、`shard_1` 两库；`performance_schema=OFF` | 省内存；stage 3 不需要元数据证据 |
| `dbdeep-restore` | 13310→3306 | 4 | `log_bin=OFF`、`performance_schema=OFF`、`read_only=OFF` | PITR 靶机只被灌数据，不需要自己的 binlog 与观测 |

- **端口为什么是 13307–13310**：沿用 `seckill-lab`「避开默认端口」的习惯（3306 常被本机 MySQL 占用），
  同时**避开 13306/16379**——那是 `seckill-lab` 自己的端口，两条 Track 可能在同一台机器上同时开着。
  `docs/依赖与离线.md` 里给出 `netstat -ano | findstr 13307` 的自检命令。
- **内存**：四个实例都设 `innodb_buffer_pool_size=128M`，`performance_schema` 只在 master 打开。
  实测内存占用写进 `docs/依赖与离线.md`，不写进 `manifest.requires`（见 §6 的说明）。
- **复制怎么起**：`docker/replica/init/02_replication_bootstrap.sh` 做三件事——① 等 master
  healthy；② 读 `SHOW MASTER STATUS` 拿**当前**的 `(file, pos)`；③ `CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='dbdeep-master', SOURCE_PORT=3306, SOURCE_USER='repl', SOURCE_PASSWORD=…,
  SOURCE_LOG_FILE=…, SOURCE_LOG_POS=…, GET_SOURCE_PUBLIC_KEY=0` 然后 `START REPLICA`。
  两处刻意的选择：**（a）用容器网络名 + 3306，不是宿主端口 13307**——从库在 compose 网络里，
  用宿主端口会连不上，这是第一次搭主从最常见的一个坑；**（b）复制账号用 `mysql_native_password`**——
  `caching_sha2_password` 在没有 TLS 的复制通道上要先做 RSA 公钥交换，本地 lab 里只会制造噪音。
  `binlog_format=ROW` 是 master/replica 的 my.cnf 默认值，测试里只改**会话级**格式（§1.4）。
- **种子数据**：`orders_stats` 5 万行（stage 5 的扫描基数）、`orders_ddl` 5 千行（影子表回填要能分批）、
  `order_0/order_1` 各留空（stage 3 自己插 20 行）、`ledger_entry` 由 stage 4 自己造。
  所有种子脚本幂等（`DROP TABLE IF EXISTS` + `CREATE` + 批量 `INSERT`）。

### 2.5 冒烟测试

`SmokeTest`（`@Tag("stage00")`）在骨架上必须**全绿**，它是环境体检，不是判据：

1. 四个实例的 `SELECT 1` 都通（含宿主端口与容器名两条路径）；
2. `SHOW REPLICA STATUS` 的 `Replica_IO_Running` / `Replica_SQL_Running` 都是 `Yes`，
   `Last_IO_Error` 与 `Last_SQL_Error` 为空；
3. `SELECT @@global.binlog_format` = `ROW`，`@@global.log_bin` = `1`；
4. `scripts/dbexec.sh dbdeep-master mysqldump --version` 与 `… mysqlbinlog --version` 有输出
   （证明恢复链路所需的二进制在镜像里，学员不需要另装 MySQL 客户端）；
5. `performance_schema` 的 `metadata_locks`、`events_statements_summary_by_digest` 可读；
6. 端口表与内存自检（读 `docs/依赖与离线.md` 里那两条命令的结果，只报告不判 fail）。
7. **【v1.1 新增】四个 SQL 迁移脚本在骨架上都能执行、且重放两次结果相同**：`V1` / `V4` / `V5` / `V6`
   依次在各目标库上执行一遍、再执行一遍，断言的是「第二次不报错、表结构与首轮一致、行数不变」。
   这一条是 `_SCALE.md` §1.1 约束 1 的体检器：它证明新增的口径载体**单线程/单机顺序执行时是对的**，
   因此新增缺陷只可能红在并发、故障或不可用输入上，不会把冒烟带红。

第 2 条若失败（例如只重启容器不删卷时，从库报 `1236 Could not find first log file name`），
冒烟测试要打印**一键修复命令**（`docker compose down -v && docker compose up -d --wait`），
并明确标注「环境未就绪」，而不是让学员去猜一个跟他无关的红。

**为什么是这个教学顺序。** 主从是后面五关的地基：在线 DDL 要看「DDL 在主库怎么影响业务、在从库怎么
排队重放」，读写分离一致性整关都建在复制语义上，PITR 的一半是 binlog。（所以 1 是根，也必须是根。）
2 与 3 的顺序取决于「先解决运维动作造成的可用性事故，还是先解决数据规模带来的正确性问题」——
我们把 DDL 放在前面，因为它的判据（元数据 + 锁排队）**完全不依赖数据量**，是六关里最先能验证
契约是否成立的一关（见 §7 实施顺序）。4 接在 3 之后：分片之后「备份恢复的范围」变成一个真问题
（一个逻辑库的 PITR 与两个分片的 PITR 不是一个动作），而 4 的判据（恢复终态）是最硬的一类。
5 放在 4 后面是为了让「证据闭环」这一课发生在学员已经见过 `EXPLAIN`、handler 计数器、元数据表
之后。6 收尾：它同时用到 1 的健康判断与 4 的 binlog 视角，是整条线唯一谈「一致性取舍」的一关。

**关于 DAG 分叉（诚实说明）。** 这条 Track 的 `progression` 是一条线性链，**没有分叉**，原因是
分支链契约本身把分叉消掉了：`prerequisites` 只决定解锁顺序，而学员的工作区内容由
`git merge origin/<stage>` 决定，链式分支要求每一级只比上一级多「本阶段测试」。若让
stage 4（PITR，只碰单库）只依赖 `db-deep-01`，学员可能带着 stage-01 的工作区去解 stage-04 的卷，
而 stage-04 的测试文件要靠 merge `stage-04` 才进来——那一次 merge 会**连带**把 stage-02/03 的测试
一起带进来，于是学员看到一堆跟自己实现无关的红。更实际的问题是：stage 3 会把应用的数据源形态
改成「两个分片库」，而 stage 4/5 的判据全部打在 master 的单库上；真做成兄弟分支，就会出现
「arrive at stage-04 但 `masterJdbc` 指向分片库」这种**红在错误的地方**的判据。所以：
**唯一可能有意义的候选分叉（03 vs 04/05）被我们主动放弃，换来一条可以照抄、不需要解冲突的链。**

所以上面的 `prerequisites`、六个分支名、`-sol` 的切出点、以及「每一级只比上一级多本阶段测试」
这条自检**全部与复核前逐字相同**；§3 的表格里只多了一列说明（见下）。这正是本轮选择「扩面而非
合并」的直接收益：若当初把 stage 3 与 stage 4 合掉（它们都碰「数据怎么落地」），就必须重算整套
依赖、重切分支，并把 §1.2 那条「红得越窄越能证明判据钉在业务缺陷上」的论证一起打掉。

扩面在链上的**唯一可见变化**是每一级的文件集合变大了，而这恰好是链式分支契约允许的：
`src/main/resources/db/migration/V1__…` 与 `V4__/V6__` 三个新增脚本、以及四个新增 Java 类
（`TwoSegmentIdAllocator` / `PitrRunLedger` / `StatsSnapshotProvider` / `RouteDecisionProvider`）
都落在**本阶段的 base 上**——它们带着缺陷，因此 `stage-NN-…` 分支上照样红；`-sol` 从同阶段 base
切出后带着参考实现，因此绿。**「新增文件必须先在 base 上带缺陷出现、再在 `-sol` 上被修好」是今天

      还带重复。用例断言的是一组**恒等关系**：第 2 页恰好等于全局有序序列的第 6 到第 10 个元素，
      且第 1、2、3 页两两不相交、并集等于全部 20 行——这是分片分页唯一能站得住的判据。它验的是
      不变量：**任意页码都不重不漏**。

      第三处，全局 ID 撞号。用例构造两个生成器实例（实例编号不同、注入**同一个固定时钟**），

      编进最终的号里，于是同一时钟下的两批号完全重合。同一个用例还验单实例连续取号严格递增，
      以及时钟被拨回去之后号仍然不重复、不倒退。它验的是不变量：**同一时刻的两个实例不得撞号**。

      第四处（v1.1 新增）打的是**另一个**不变量：**号段的发放必须由数据库的约束兜住，不能靠时序
      恰好不冲突**。用例用一个固定闸门让两个分配器**在同一时刻**各自领一段，然后断言两件离散事实：
      `id_lease` 里同一个号段区间恰好只有一行；两个实例最终拿到并发出的号，并集里没有重复元素。
      骨架的分配器是「先查最大、再插一行」两个动作，两个实例会各自算出同一段并都插进去——单机串行

      不靠这次有没有恰好撞上。

      骨架上本来就【绿】的用例有三条，留着它们是刻意的：① 分片库结构体检（两个库都在、两张表同构、
      分片数是 2）；② 单实例连续取号严格递增（发号器的快乐路径）；③ 第 1、2、3 页两两不相交

      边界/拒绝路径那一条：**页码超过数据量时**，分页实现必须返回空集并给出正常结果，

## Stage 2 · 在线 DDL 与锁表 ⬜

**亲手场景**：一个排队中的 ALTER 把后面所有写请求堵死（你亲手用未提交事务做出了这个前提），
你再让加列变成「只改元数据」并给出事后可查的证据。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 三种算法 | COPY 重建并拷贝、INPLACE 原地改、INSTANT 只改数据字典 | online DDL 的算法差别与代价？ |
| INSTANT 的边界 | 只有少数变更能只改元数据，越界会直接报错而不是静默降级 | 哪些 DDL 能 INSTANT？怎么确认它真的 INSTANT 了？ |
| 元数据证据 | `information_schema.INNODB_TABLES` 的行版本计数能事后区分「改元数据」与「重建表」 | 怎么证明一次 DDL 没有重建表？ |
| MDL | DDL 要元数据写锁，未提交事务持元数据读锁 | 加个字段为什么能把整张表写死？ |
| 锁队列饥饿 | 等待中的 DDL 会把之后到达的写请求一起堵在队列里 | 长事务为什么会让 DDL 变成故障？ |
| 影子表迁移 | 建影子表 → 分批回填 →（追增量）→ 原子换名 | gh-ost / pt-osc 的原理与风险？ |
| 原子切换 | 一条 RENAME 语句可以同时换多个表名，对外没有「表不存在」的窗口 | 为什么不能 DROP 之后再 RENAME？ |
| **可重跑的迁移**（v1.1） | 迁移是一个可能被中断、被重试、被回滚的多步动作；「搬到哪了」必须是一条能读出来的记录，重跑才能只补没做过的部分 | 迁移脚本被中断了怎么办？怎么保证重跑不会搬两遍？ |
| **有界等待与失败分类**（v1.1） | 拿不到 MDL 和 SQL 写错是两类失败：前者过一会儿可以重试，后者重试一万次也一样；混成一个异常等于把运维最需要的信息丢掉 | DDL 拿不到锁，代码该怎么处理？ |

**复现命令**：
```sql
-- 会话 A：持锁（不要提交）
START TRANSACTION WITH CONSISTENT SNAPSHOT; SELECT id FROM orders_ddl LIMIT 1;
-- 会话 B：ALTER（它会排进队列）
ALTER TABLE orders_ddl ADD COLUMN channel VARCHAR(32) NOT NULL DEFAULT 'h5';
-- 会话 C：普通写入（把它堵到你怀疑人生）
SET SESSION lock_wait_timeout = 2; INSERT INTO orders_ddl (id) VALUES (1);
```

## Stage 3 · 分库分表 & 全局 ID ⬜

**亲手场景**：两个库各放 10 行，你要让第 2 页恰好等于全局第 6–10 行；写进去的订单必须能按同一个
键读回来；两个实例在同一毫秒取号不许撞。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 分片键选择 | 选能定位到单分片、分布均匀的列；查询不带它就得多库扫描 | 分片键怎么选？选错了怎么补救？ |
| 路由一致性 | 同一行的读写必须由同一个键、同一处算法决定落在哪 | 读写路由不一致会出现什么现象？ |
| 跨库分页 | 全局偏移量不能下推到各分片，各库的 OFFSET 语义是「自己内部」的 | 分库分表后怎么做分页？ |
| 归并与二次查询 | 内存归并简单但深翻页要取 N×每页；二次查询靠排序键回各库捞 | 深分页怎么优化？ |
| 全局 ID | 号段、雪花等方案的共同点：把「唯一性」编进号本身，而不是靠数据库自增 | 分库分表后主键怎么生成？ |
| 时钟回拨 | 依赖时间的发号器必须处理回拨，否则重复或倒退 | 雪花算法遇到时钟回拨怎么办？ |
| 扩容迁移 | 翻倍扩容时有一半数据要搬家，靠双写/影子表 + 对账收敛 | 分片数怎么定？扩容怎么平滑？ |
| **号段模式**（v1.1） | 一次领一段、内存里发完再领下一段；唯一需要协调的是「领段」这一步，而它必须由数据库的约束兜住 | 号段发号器怎么保证两个实例不领到同一段？ |
| **并发领段的原子性**（v1.1） | 「先查最大号段、再插一行」是检查-然后-行动；单机串行正确，两个实例同时领就会各自算出同一段 | 号段分配的竞态怎么消除？靠锁还是靠约束？ |

**复现命令**：
```sql
-- 两个逻辑库各自的行，交给你的分页实现
SELECT id, created_at FROM shard_0.order_0 ORDER BY created_at, id;
SELECT id, created_at FROM shard_1.order_1 ORDER BY created_at, id;
-- 全局第 2 页（每页 5 行）必须恰好是 20 行全局有序序列的第 6–10 个
```

## Stage 4 · binlog 与 PITR 恢复 ⬜

**亲手场景**：一次误删之后，你拿着凌晨的全备和从那时起的 binlog，把库恢复到「误删之前的那一瞬间」，
并且连跑两次结果一样。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 全备 + 增量 | 全备给基线，binlog 给变更，两者接缝靠备份时记录的坐标对齐 | PITR 的原理是什么？ |
| 备份的位点 | 全备必须记下自己对应的 binlog 文件与位置，否则增量无从接起 | 为什么备份要带 binlog 坐标？ |
| 恢复边界 | 按位置精确；按时间有同秒多事务的模糊 | 「恢复到某个时间点」精确吗？ |
| redo 与 binlog | 内部 redo 与归档 binlog 靠两阶段提交保持一致：prepare → 写 binlog → commit | 两阶段提交解决什么问题？组提交呢？ |
| 可重复演练 | 恢复必须可反复执行：每轮开始前目标状态要由恢复方自己保证 | 为什么说「没验过的备份等于没有备份」？ |
| 恢复范围 | 分片之后「一个逻辑库的 PITR」与「整个集群的 PITR」不是同一个动作 | 分库分表下怎么做恢复？ |
| **坏输入先拒绝**（v1.1） | 备份文件不存在/为空、位点早于全备坐标、位点落在已清理的 binlog 区间——这些都必须在**灌任何数据之前**判定；「跑完了但是半成品」比「立刻失败」危险得多 | 恢复演练里最危险的结果是什么？ |
| **恢复台账**（v1.1） | 每轮恢复无论成败都留下一行：轮次、输入、目标位点、结局；「这次没做」也是一条必须留痕的事实 | 出了事故，怎么知道上一次恢复是谁用什么输入跑的？ |

**复现命令**：
```bash
S=dbdeep-master; R=dbdeep-restore
bash scripts/dbexec.sh $S mysqldump --single-transaction --source-data=2 --databases dbdeep_lab > /tmp/full.sql
# 误删之前取位点
bash scripts/dbexec.sh $S mysql -uroot -pbagu1234 -e "SHOW MASTER STATUS\G"
# 恢复：先基线，再按位点重放增量（位点从备份头与上面那条命令里取）
```

## Stage 5 · 慢 SQL 治理闭环 ⬜

**亲手场景**：心跳查询霸占「最慢」榜首，真正的全表扫描排在后面；你改用扫描量挑目标，并让改写前后
的对比成为别人能复跑的证据。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 发现的两条路 | 慢日志按耗时阈值记（会漏会漂），digest 表按扫描量与次数聚合 | 慢查询怎么发现？慢日志有什么盲区？ |
| 索引失效 | 列上函数、隐式类型转换、前导模糊都会让普通索引用不上 | 为什么索引没走？怎么改写？ |
| EXPLAIN | `type` / `key` / `rows` / `Extra` 判断访问路径 | EXPLAIN 主要看哪几个字段？ |
| Handler 计数器 | 顺序扫描与索引读走的是不同计数器，可以量化「扫了多少行」 | 怎么量化一条查询扫了多少行？ |
| 改写保语义 | 谓词要落在列上，但结果集必须逐值相等 | 函数包列的写法怎么改写？ |
| 证据闭环 | 发现 → 改写 → 访问路径与扫描量对比 → 结果一致性回归 | 优化完怎么证明有效？ |
| **证据快照**（v1.1） | 访问路径、扫描量、语义校验和必须**一次采集**；分三次去问就会读到不同语句的读数，三项对不上 | 为什么优化前后的读数必须在同一次采集里拿到？ |
| **空结果的边界**（v1.1） | 「这一天没有数据」是一个正常的空结果（0 行、校验和为 0），不是异常；出具证据的东西自己对边界的表现必须确定 | 统计口径遇到空数据集应该返回什么？ |

**复现命令**：
```sql
SELECT DIGEST_TEXT, ROWS_EXAMINED, SUM_TIMER_WAIT/1e9 AS sec
FROM performance_schema.events_statements_summary_by_digest
ORDER BY ROWS_EXAMINED DESC LIMIT 5;
SHOW SESSION STATUS LIKE 'Handler_read%';
```

## Stage 6 · 读写分离一致性取舍 ⬜

**亲手场景**：把从库冻住之后，「写后读」与「普通读」走了不同的库，并且每一次读的决策都能被审计。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 读写分离 | 写主读从，用「可能读到旧数据」换吞吐与主库负载 | 读写分离怎么实现？代价是什么？ |
| 写后读一致 | 同一会话写完立刻读必须回主库（粘滞/强制走主），否则用户自己看不见自己 | 主从延迟导致读不到自己写的数据怎么办？ |
| 决策可观测 | 每次读记录走了谁、依据是什么、是否可能陈旧 | 怎么排查「用户读到了旧数据」？ |
| 一致性分级 | 读己之写、单调读、最终一致要按业务分别声明，而不是全局开满 | 哪些业务可以接受最终一致？ |
| 半同步复制 | 主库等至少一个从库确认收到（甚至应用）才提交，把异步窗口压到最小 | 半同步与异步差在哪？无损复制呢？ |
| 从库可用性 | 从库落后或线程停掉时，路由必须知道，而不是继续送流量 | 从库挂了/落后了，读流量怎么办？ |
| **审计保留口径**（v1.1） | 审计记录必须可清理，但读数要把「被清理掉多少条」如实报出来；否则「被淘汰」在读数里就等于「没发生过」 | 只留最近 N 条审计记录，怎么保证它还是可信的？ |
| **拒绝而不是静默兜底**（v1.1） | 从库确定不可读时，普通读应当快速失败并给理由；悄悄改打主库会把「从库坏了」这件事藏起来 | 从库不可读时该降级还是该报错？ |

**复现命令**：
```bash
R=dbdeep-replica
bash scripts/dbexec.sh $R mysql -uroot -pbagu1234 -e "STOP REPLICA SQL_THREAD;"   # 冻住从库
# 现在「写后读」与「普通读」分别读到什么、决策记录分别是什么
bash scripts/dbexec.sh $R mysql -uroot -pbagu1234 -e "START REPLICA SQL_THREAD;"
```

**判定面逐条论证**（每条都要能在骨架里匹配到东西——写错一个字母就是静默漏洞）：

| 路径 | 为什么它是「判据所依赖的东西」 | 学员为什么不许改 |
|---|---|---|
| `./src/test/` | canonical 测试与四个 fixture 脚本本身就是红绿判据；测试里固化了「误删前取位点」「持 MDL 造队列」「注入固定时钟」这些确定性手法 | 改了测试就是改判据；`seckill-lab` 已经确认这是最便宜的一条作弊通道 |
| `./pom.xml` | 构建配置决定测试跑不跑、跑哪一组（`-Dgroups`）、以及 surefire 的失败策略 | 一个 `<skipTests>` 或换一个 surefire 版本就能让判据失效 |
| `./scripts/` | `build.sh` 是准入门的构建入口；`digest-pin.sh` 生成所有 pin；`dbexec.sh` 是**判据与容器之间的唯一通道**（PITR 的 `mysqldump`/`mysqlbinlog` 全走它） | 把 `dbexec.sh` 指向别的服务、或去掉 `-T` 改变输出行为，都能在不碰业务代码的情况下伪造判据 |
| `./docker/` | 四个实例的镜像、端口、`my.cnf`、init 脚本与复制 bootstrap 共同定义了「判据跑在什么环境上」：`binlog_format=ROW` 的全局默认、`performance_schema` 的开关、`read_only` 与 `super_read_only` 的时序、【v1.1】`binlog_expire_logs_seconds` 的取值（Stage 1 的「位点过期」边界用例靠它定义「保留期」是什么） | 关掉 `performance_schema` 就能让 Stage 2/5 的元数据证据消失；把 `read_only` 去掉就能让 Stage 6 的「冻结从库」前提失效；把 binlog 保留期调大就能让 Stage 1 的「不可用」边界用例失去构造前提 |

**【v1.1】四个新增文件为什么**不在**判定面里**：`V1__stage01_replication_progress.sql`、
`V4__stage04_pitr_run_ledger.sql`、`V6__stage06_route_decision.sql` 三个脚本，以及
`TwoSegmentIdAllocator` / `PitrRunLedger` / `StatsSnapshotProvider` / `RouteDecisionProvider` 四个类，
都是 **`scope.files_to_change` 里的待改文件**——它们带着缺陷（见 §2.3 的 D-D / D-L / D-N / D-P / D-S），
学员必须能改它们。判定面的判据只有一条：「改了它 → 验收门直接 fail」，而 §6 的原则是
**判定面只放判据所依赖的东西，学员要改的业务文件不在其中**。这也正是本项目里最容易写错的地方：
`src/main/resources/db/migration/` 的四个脚本「看起来像基础设施」（同目录里确实有 compose 的生命周期），
但它们全部属于改动面；把它们误列进 `protected_paths` 会让《准入门》的
「判定面每条都要能匹配到东西」这一条仍然通过，却在运行期把所有学员的正当修改判成越界——
**一个静默漏洞**。因此 §8 的自查清单里把这一条单独列了出来。

**必须 pin 的东西**：

- **三个文件入口**（`compose` / `build` / `tests`）：由 `scripts/digest-pin.sh` 按「路径解析成文件集 →
  CRLF→LF 归一化 → 逐文件 sha256 → 按相对路径 C 序拼成 `<sha>  <path>\n` → 再取一次 sha256」的
  Merkle 式配方生成（与 `seckill-lab` 同一套配方，直接复用它的脚本头注释）。
- **镜像摘要**：四个实例**用的是同一个 image ref `mysql:8.0`**，所以只 pin 一条 `mysql:`。
  为什么不写四条：同一 ref 在同一架构上拉到的多架构 manifest 摘要必然相同，写四遍只会制造
  四份会一起过期、又必须一起更新的冗余值。**什么时候必须拆成两条**：一旦 master/replica 与
  shard/restore 用了不同的小版本或不同发行（哪怕是 `mysql:8.0` 与 `mysql:8.0.36`），就必须
  拆成两条 pin，因为它们会各自漂。取值方式与 `seckill-lab` 一致：
  `docker image inspect mysql:8.0 --format '{{index .RepoDigests 0}}'`。注意 digest 与架构绑定，
  arm64 机器上的取值会不同，届时按本机 `digest-pin.sh` 的输出更新。
- **CI 侧**：`contribute.review.ci: paper validate-track` 会跑静态门；本 Track 的「基础设施可起」
  这一条尤其重要——四个实例加一次复制 bootstrap 比 `seckill-lab` 的两容器慢得多，
  建议 CI 单独给这一项一个较长的超时，并把 `docker compose up -d --wait` 的等待时间算进去。

**供应链注意**：

1. 本 Track 会在学员机器上执行的东西有：四个 MySQL 容器（官方镜像，pin 摘要）、三个 shell 脚本
   （`build.sh` / `digest-pin.sh` / `dbexec.sh`，全部 pin 文件摘要）、以及 canonical 测试本身
   （`mvn test`，pin `tests` 入口）。**没有第三方二进制**，不下载 gh-ost / pt-osc——
   影子表方案由学员自己在 Java 里实现，这也是它可被判据覆盖的原因。
2. `scripts/dbexec.sh` 是本 Track 唯一新增的「可执行桥」，它的实现要刻意小（一行
   `docker compose -f docker/docker-compose.yml exec -T "$@"`），并且**永远不带 `--privileged`、
   不挂载宿主目录进容器**。它把命令执行面收窄成「在四个已知服务里跑已知二进制」。
3. **ShardingSphere-JDBC 坐标预置在 pom 里，属可选实现**。它是纯 Java 依赖、随 Maven 构件解析，
   不产生运行时进程。因此 `docs/依赖与离线.md` 必须写清：版本号钉死（禁止 `LATEST`/范围版本）、
   首次构建需要网络拉依赖、离线跑法用 `mvn -o`，并提供 `mvn dependency:go-offline` 的预热命令。
   这是本 Track 离线复现的唯一软肋，写进 §7 风险表第 1 条。
4. `manifest.requires` 只声明 `java` / `build` / `docker` 三个键。**内存（≥6GB）与端口
   （13307–13310）不写进去**：它们是真实前置，但自造键名有撞 schema `additionalProperties: false`
   的风险，而这两项由 `SmokeTest` 第 6 条报告、由 `docs/依赖与离线.md` 给自检命令，效果一样、
   风险为零。若将来 schema 明确承认更多 requires 键，再把它们提上来。

**trust_level 建议**：起步 `self`（自托管、自己写的）。**不建议起步就报 `community`**：
`community` 是「第三方贡献、默认不完全信任」，而本 Track 的攻击面比 `seckill-lab` 大一档——
它起四个容器、跑 `mysqldump`/`mysqlbinlog`、还会按学员代码里的参数重建库。升 `verified` 的条件是
`contribute.review.signed_by` 有维护者背书 + 全部入口被 `digest_pin` 锁定 + CI 在隔离环境里跑过一次
（含 compose healthy 与六个 stage 的红绿判别性），这三条缺一条都不该升。

## 7. 风险、妥协与工作量

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **离线构建**：`mvn -o` 需要本地仓库已预热（Spring Boot + ShardingSphere-JDBC 依赖树不小） | 学员首次构建失败 → 看起来像「骨架坏了」 | `docs/依赖与离线.md` 给 `mvn dependency:go-offline` 预热命令；`scripts/build.sh` 默认 `-o` 并在失败时打印这句提示；`SmokeTest` 第 6 条报告本地仓库是否存在关键构件 |
